# اتفاقية العمل والاعتماد

> كيف يُدار تنفيذ OpsOne بين مالك المنتج وجلسات Claude ومسؤول السيرفر. تُطبَّق مع [`project-plan.md`](project-plan.md)
> و[`decisions/open-questions.md`](decisions/open-questions.md) وقواعد `CLAUDE.md` و`.claude/rules/*`. عند التعارض تُقدَّم قواعد الأمان والمستودع.

## 1. الأدوار

| الدور | من | المسؤولية | لا يفعل |
|---|---|---|---|
| مالك المنتج | المستخدم | يعتمد الخطة ونطاق كل مرحلة وقرارات المنتج ودمج المراحل، ويجري UAT | لا يشغّل أوامر ولا يراجع كودًا سطرًا بسطر |
| المدير | جلسة Claude الرئيسية | يقسّم المرحلة إلى جلسات، يكتب الموجز لكل جلسة، يراجع النتائج، يدير سجل القرارات، يدفع الفروع ويفتح الـ PRs، يؤرشف الجلسات المنتهية، يقدّم التقارير | لا يكتب كود النطاقات بنفسه؛ لا يدمج في `main` دون G3 |
| جلسة عاملة | جلسة Claude لكل قطعة عمل | تنفذ قطعتها فقط على فرعها، تكتب الاختبارات والمساعدة، تلتزم (commit)، وتعيد تقريرًا قصيرًا | لا تلمس ملفات جلسة أخرى، لا تدفع إلى `main`، لا تفتح جلسات جانبية دون حاجة |
| مسؤول السيرفر | شخص يحدده مالك المنتج | الاستضافة، Traefik والنطاقات وTLS، الأسرار، النسخ الاحتياطي، النشر لكل منشأة | لا يقرأ بيانات المنشآت بصفته التشغيلية |

### حجم النموذج لكل جلسة

| الحجم | متى |

## 2. بوابات الاعتماد

### G1: الخطة ونطاق كل مرحلة

- قبل أي مرحلة يرسل المدير **بطاقة بدء** (انظر §3) ويبدأ بعد موافقة مالك المنتج.
- اعتماد هذه الخطة نفسها = G1 للمرحلة التالية فقط؛ كل مرحلة لاحقة لها G1 خاصة.
- تغيير نطاق مرحلة جارية (إضافة/حذف متطلب) يعيد G1 لهذا التغيير فقط.

### G2: قرارات المنتج

- كل قرار في سجل واحد: [`decisions/open-questions.md`](decisions/open-questions.md)، بتوصية لكل بند.
- يعرض المدير البنود الموقِفة للمرحلة القادمة كأسئلة بأزرار اختيار (زر التوصية أولًا)، مجمّعة، مرة واحدة لكل مرحلة قدر الإمكان.
- بند **قابل للرجوع** لم يُجب عند بدء مرحلته ← `decided-default` بالتوصية، ويُذكر في وصف الـ PR تحت «قرارات افتراضية» ليمكن عكسه.
- بند **غير قابل للرجوع** (مال، أمن، عقد خارجي، تكلفة، نص قانوني) لا يأخذ افتراضيًا؛ يوقف القطعة المعتمدة عليه فقط، ويستمر الباقي.
- القرار المعتمد يُحدّث في السجل (`decided`)، والمعماري منه يُكتب ADR في `docs/decisions/`.

### G3: دمج المرحلة في `main`

شروط الطلب (كلها):

1. CI أخضر (Pint، Larastan، Pest، typecheck، build).
2. مراجعة المدير (`/code-review`)، ومراجعة أمنية (Opus) للمراحل P2، P3، P6، P7، P8.
3. ملاحظات عرض قصيرة بالعربية في وصف الـ PR: ما الذي يعمل، كيف يُجرَّب، لقطات شاشة (عربي/إنجليزي، فاتح/داكن، جوال)، القرارات الافتراضية، ما لم يُنفَّذ ولماذا.
4. Definition of Done (§5) متحقق.

ثم يطلب المدير الموافقة على الدمج، ويدمج بعد «نعم» صريحة.

### G4: إجراءات تحتاج سؤالًا دائمًا

| الإجراء | ملاحظة |
|---|---|
| الدمج في `main` | حتى لو كان CI أخضر |
| النشر إلى dev/stage/prod أو أي تغيير على خادم | بتسمية البيئة والهدف |
| الأسرار وبيانات الدخول | إنشاء، تدوير، `APP_KEY`، مفاتيح الترخيص، مفاتيح المزودين |
| حذف بيانات أو أفعال هدامة | `migrate:fresh`، `db:wipe`، حذف volumes، `git reset --hard`/`clean -f`، حذف فروع غير مدموجة |
| الحسابات والتكاملات الخارجية | إنشاء حساب لدى مزود، ربط بوابة دفع/SMS/بريد حقيقية، webhooks خارجية |
| الأسعار والنصوص القانونية | أسعار الباقات، الشروط، سياسة الخصوصية والاحتفاظ |
| تغيير قرار `decided` أو ADR | |

### بلا اعتماد

إنشاء الجلسات وأرشفة المنتهي منها، إنشاء الفروع، الالتزامات (commits)، الدفع إلى فروع الميزات والتكامل، فتح PRs ودمج PRs الجلسات في **فرع تكامل المرحلة**، إصلاح CI، تحديث الوثائق وسجل القرارات بالتوصيات، تشغيل الاختبارات والحاويات محليًا، اختيار تفاصيل تقنية داخل القواعد المعتمدة.

## 3. الإيقاع والتقارير

### بطاقة بدء المرحلة (من المدير، قبل G1)

| البند | المحتوى |
|---|---|
| الهدف والنطاق | المعرفات (SRS، P، M) والشاشات |
| خارج النطاق | ما أُجّل صراحة |
| القرارات الموقِفة | روابط Q-xx بأزرار |
| الجلسات | القطع، النموذج لكل قطعة، ما يتوازى، الملفات المملوكة |
| التقدير | أيام العمل والمخاطر |

### تقرير نهاية المرحلة (مع G3)

ما أُنجز مقابل المعرفات، نتائج الاختبارات الفعلية (أوامر ونتائج، لا ادعاء بلا دليل)، السيناريوهات العابرة التي أصبحت تنجح، القرارات الافتراضية، الانحرافات وADRs، ما بقي، والمرحلة التالية.

### أثناء المرحلة

- تقرير يومي قصير من المدير: المنجز، الجاري، المعطّل.
- **العوائق:** الجلسة العاملة ترسل سؤالًا واحدًا للمدير وتتوقف؛ المدير يجيب من الوثائق أو القواعد، وإلا يحوّله إلى بند في السجل (G2). لا تخترع جلسة قاعدة أعمال غير موثقة.
- خطأ في الوثائق يُسجَّل في السجل ولا يُصحَّح ضمنيًا في الكود.

## 4. الفروع والـ PRs

| النوع | الاسم | يدمج في |
|---|---|---|
| تكامل المرحلة | `phase/p<N>-<slug>` (مثال `phase/p2-org-access`) | `main` عبر G3 |
| قطعة جلسة | `feat/p<N>-<slug>` (مثال `feat/p2-license-verifier`) | فرع تكامل المرحلة |
| إصلاح | `fix/<slug>` | الفرع المتأثر، أو `main` عبر G3 |
| وثائق | `docs/<slug>` | `main` عبر G3 |

- عنوان الـ PR: `[P<N>] <وصف قصير>`؛ الوصف يذكر المعرفات المغطاة، الاختبارات، القرارات الافتراضية، ولقطات الشاشة.
- الالتزامات بصيغة Conventional Commits (`feat:`، `fix:`، `docs:`، `test:`، `chore:`).
- جلستان لا تعدّلان الملفات نفسها في الوقت نفسه؛ الملفات المشتركة (routes، `lang/`، الترحيلات المشتركة) يملكها المدير أو قطعة واحدة في كل مرحلة.
- الترحيلات متوافقة للخلف دائمًا (ADR-0002: المنشآت تُرقّى في أوقات مختلفة).

## 5. Definition of Done

ميزة أو قطعة لا تُعد منجزة إلا إذا:

| البند | الشرط |
|---|---|
| السلوك | يحقق معيار قبول كل معرّف SRS مذكور، ويرفض الحالة المقابلة بلا أثر جزئي |
| الصلاحيات | اختبار ثلاثي لكل P-xx: مخول بنطاق صحيح، مخول خارج النطاق، غير مخول؛ والتحقق في الخادم لا بالإخفاء |
| الحالات | اختبار لكل انتقال M-xx منفذ، مسموح ومرفوض، مع سجل الانتقال |
| المال والمخزون | اختبارات التزامن والتكرار للأفعال المؤثرة؛ السيناريوهات العابرة المعنية تنجح حرفيًا |
| الجودة | Pint، Larastan، Pest، `tsc --noEmit`، build خضراء؛ لا `any`؛ تحقق Form Request |
| اللغتان | كل النصوص في `lang/ar` و`lang/en`؛ الشاشة مُراجعة بالعربية RTL والإنجليزية LTR |
| الجوال والمظهر | الشاشة مُراجعة على 390px والحاسوب، وفاتح وداكن؛ لا خصائص فيزيائية (`ml-`/`left-`) |
| الوصول | لوحة المفاتيح، تسميات الحقول، حالات لا تعتمد على اللون وحده |
| المساعدة | مقال مساعدة عربي/إنجليزي محدّث للميزة، والبحث والروابط تعمل (NFR-18) |
| الوثائق | `docs/` محدّثة عند تغيّر البنية، ADR لأي انحراف، `docs/tech-stack.md` لأي حزمة جديدة، وسجل القرارات محدّث |
| الأمان | لا أسرار في الكود أو السجلات؛ لا تسجيل لبيانات شخصية أو دفع |
