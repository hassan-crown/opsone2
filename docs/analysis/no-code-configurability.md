# تحليل: جعل OpsOne قابلاً للتهيئة بلا كود (No-Code Configurability)

> الحالة: تحليل وتصميم فقط — لا يغيّر أي كود منتج. مبني على قراءة `src/` على `origin/main` (2026-11-02) والـ ADRs
> 0005–0032. ZATCA (فوترة إلكترونية) في PR منفصل ولم يُدمج بعد؛ يُذكر هنا كقيد فقط.
>
> المصطلحات: «المنشأة» = عميل OpsOne (instance مستقل)، «المالك/المدير» = من يهيّئ، «العميل» = عميل المنشأة النهائي.

## 0. الخلاصة التنفيذية

1. OpsOne **ليس صلباً بالكامل**: المسار (flow) قابل للتحرير ومُرقَّم الإصدارات ومثبّت لكل طلب، وهناك ~10 جداول إعدادات
   (`finance_settings`, `work_settings`, `discount_limits`, `commission_settings`, `return_settings`, …). لكن
   **القواعد التي تختلف فعلاً بين الشركات** — جدول الدفعات، محفّزات الاستحقاق، التذكيرات، نصوص الرسائل، بنود العقد،
   الترقيم، حدود الموافقات — **ثابتة في الكود**.
2. أهم ثغرة: **نسبة الدفعة الأولى معرّفة في مكانين مستقلين** — في قالب المسار (`payment_check` بقيمة 50) وفي قالب الجدول
   (`OrderSchedule::TEMPLATES['half']` = 5000bp) — ويربطهما مفتاح نصي (`first`/`final`) فقط. المالك الذي يغيّر أحدهما
   لا يغيّر الآخر. أي حل No-Code للدفعات يبدأ بتوحيد المصدر.
3. التوصية المعمارية: **لا نبني «Low-Code platform» عامة**. نبني ثلاث طبقات محددة الأنواع (typed) فوق ما هو موجود:
   - **Settings موسّعة** (قيم وسياسات) — رخيصة وسريعة.
   - **Configuration Release** مُرقّم (draft → publish → pinned per order) يجمع المسار + خطط الدفع + السياسات، بنفس نمط
     `flows/flow_versions` الموجود.
   - **Automation Engine** (حدث → شرط → إجراء) يستهلك `state_transitions` والأحداث الموجودة، وينفّذ عبر
     الـ Actions والـ Outbox الحالية فقط، **ولا يكتب في الدفتر المالي أو المخزون أبداً**.
4. المرحلة 1 (S–M): خطط دفع قابلة للاختيار + إعدادات تذكير + ترقيم + بنود عقد + نصوص رسائل. المرحلة 2 (L): محرّك
   الأتمتة + نموذج خطط الدفع الكامل مع البوابات والإصدارات والمحاكاة. المرحلة 3 (L): Builders (حقول مخصصة، نماذج،
   قوالب مستندات، سلاسل موافقات، تقارير).

## 2. لكل بند: ما يريده العميل، الآلية، الخطر، الضوابط

مفتاح الآليات: **SET** إعداد · **RULE** قاعدة شرط→إجراء · **TRIG** محفّز حدث/مؤقّت · **FORM** باني حقول/نماذج ·
**TPL** محرّر قوالب · **FLOW** مصمّم المسار · **APPR** سلسلة موافقات · **FX** حقل معادلة · **SCHED** أتمتة مجدولة.
مفتاح الخطر: 💰 سلامة المال · 🧾 ZATCA/VAT · 📜 تدقيق · 🔗 اتساق البيانات · 🔒 أمن.

## 3. المثال الكامل: جداول الدفعات (Payment Plans)

### 3.1 الهدف والمبادئ

- **مصدر واحد للحقيقة**: خطة الدفع تحدّد **المبالغ والاستحقاق**؛ المسار يحدّد **أين يتوقف العمل**. تربطهما **دفعة**
  (مفتاح `reference`) لا نسبة مكررة. ينتهي ازدواج P9.
- **مثبّتة لكل طلب**: الطلب يحتفظ بإصدار الخطة الذي بدأ به، كما `order_workflows.flow_version_id`.
- **المال لا يُعاد حسابه بصمت**: كل ما في ADR-0014 يبقى (الدفتر append-only، التخصيص الأقدم أولاً، `rest` يمتص التقريب،
  لا تغيير لدفعة عليها تخصيص).

### 3.2 نموذج البيانات المقترح

```text
payment_plans                       -- قالب على مستوى المنشأة (مثل flows لكن متعدد)
  id, key (unique, slug), name {ar,en}, status (active|archived),
  draft JSON, lock_version, published_version_id, is_default (unique partial),
  applies_to JSON  -- شروط اختيار تلقائي: فئات منتج، نطاق قيمة، فرع، نوع عميل
payment_plan_versions               -- immutable (الموديل يرفض update/delete)
  id, payment_plan_id, number, definition JSON, definition_hash,
  published_by, published_at, release_id NULL  -- انظر 4.2
order_finances (+)                  -- موجود؛ يُضاف:
  payment_plan_version_id NULL      -- مثبّت عند إنشاء الجدول
order_dues (+)                      -- موجود؛ يُضاف:
  trigger JSON          -- {event, stage_key?, offset_days, anchor: after|before}
  grace_days INT
  reminder_policy JSON  -- نسخة مجمّدة من سياسة الدفعة
  due_on DATE NULL      -- يُثبّت عند وقوع الحدث (بدل الحساب كل قراءة فقط)
  plan_line_key
due_events_log                       -- اختياري: وقت وقوع كل محفّز لكل طلب (لتسريع DueCalendar)
  order_id, event, stage_key, occurred_at, source_ref  (unique order+event+stage)
```

`definition` لإصدار الخطة:

```json
{
  "lines": [
    {"key": "first",  "name": {"ar": "الدفعة الأولى", "en": "First"},
     "basis": "percent", "value_bp": 5000,
     "trigger": {"event": "contract.approved"},
     "grace_days": 0,
     "reminders": {"before_days": [2], "on_due": true, "after_days_every": 7, "max_after": 4,
                   "escalate_after_days": 14, "escalate_to": "order_assignee"}},
    {"key": "second", "name": {"ar": "قبل التركيب"}, "basis": "percent", "value_bp": 4000,
     "trigger": {"event": "stage.started", "stage_key": "install", "offset_days": -3}},
    {"key": "final",  "name": {"ar": "بعد الاستلام"}, "basis": "rest",
     "trigger": {"event": "delivery.completed", "offset_days": 15}, "grace_days": 3}
  ],
  "rounding_line": "final"
}
```

**كتالوج المحفّزات (مغلق، في الكود):**

| المفتاح | يقع عند | المصدر الحالي |
|---|---|---|
| `agreement.approved` | اعتماد أول اتفاق | `AgreementApplied` (موجود = `agreement`) |
| `contract.approved` | موافقة/توقيع العقد | M-08-T02 على مستند kind=contract |
| `design.approved` | موافقة التصميم | M-08-T02 kind=design |
| `measurement.final` | تحقق إجراء القياس النهائي | M-27 على `record_measurements` |
| `stage.started` + `stage_key` | بدء مرحلة | M-06-T01 (يعمّم `payment_stage`) |
| `stage.completed` + `stage_key` | اكتمال مرحلة | M-06-T04 |
| `delivery.first` / `delivery.completed` | أول/اكتمال التسليم | `DeliveryConfirmed` |
| `installation.done` | تحقق إجراء التركيب | M-27 على `work_task` بوسم `installation` |
| `date` | تاريخ ثابت | موجود |
| `offset_days` (±) | إزاحة على أي مما سبق | جديد |

قاعدة: `before` (إزاحة سالبة) مسموحة فقط لمحفّز **يمكن توقّعه** (`stage.started` له تاريخ مخطط من `target_days`، أو `date`)؛
وإلا يصبح الاستحقاق «عند الحدث» مع تحذير في الفحص. نتجنب بذلك «قبل التركيب بـ 3 أيام» على حدث لا تاريخ مخطط له.

**البوابات**: لا تُخزّن في الخطة بل في المسار، عبر توسيع `payment_check`:

```text
payment_check.inputs = {reference: "first", basis: "due_paid", min_bp_of_due: 10000}
```

- `due_paid`: محقّق حين يكون المخصّص للدفعة `first` ≥ `min_bp_of_due` من مبلغها.
- `amount|percent|remaining` القديمة تبقى مدعومة للإصدارات المنشورة سابقاً (لا كسر).
- `FlowCheck` يرفض `due_paid` على مرجع غير موجود في **الخطة الافتراضية المنشورة** (أو في أي خطة نشطة)، ويحذّر إن كانت
  الدفعة تستحق **بعد** المرحلة التي تحجبها (بوابة لا يمكن فتحها إلا بتجاوز).

**التجاوز (override)**: يبقى `T04AllowProceed` (P-35) مع إضافة:
`allow_proceed_limits` لكل دور/عضو (`max_shortfall_bp` و/أو `max_shortfall_minor`)، سبب إلزامي، ملف اختياري، إشعار
للمالك، `audit_events`. التجاوز لا يغيّر الدفعة ولا يلغيها؛ تظهر في «النواقص» (`shortfalls`) كما اليوم.

### 3.3 تدفق واجهة الإدارة

1. **الإعدادات ← المبيعات ← خطط الدفع**: قائمة الخطط (الافتراضية مُعلّمة)، زر «جديدة من قالب» (قوالب الصناعة، 4.5).
2. **محرّر الخطة** (مسودة): جدول أسطر — الاسم، الأساس (نسبة/مبلغ/الباقي)، القيمة، «تستحق عند» (قائمة منسدلة من
   الكتالوج + مرحلة عند الحاجة + «بعد/قبل N يوم»)، المهلة، التذكيرات (لوحة جانبية).
   - شريط علوي حي: المجموع = 100% ✓ / ناقص 10% ✗.
   - عمود «يحجب»: يقرأ المسار المنشور ويعرض «يحجب: التصنيع» مع رابط «أضف بوابة» يفتح مسودة المسار على المرحلة.
3. **شروط الانطباق** (اختياري): «تُستخدم تلقائياً للطلبات التي: فئة المنتج ∈ {ألمنيوم}، القيمة ≥ 50,000».
   أولوية صريحة عند التعارض؛ وإلا الافتراضية.
4. **المحاكاة**: «جرّب على طلب» — يختار طلباً قائماً أو قيمة افتراضية 37,500 ريال → جدول بالمبالغ بالهللة، تواريخ
   الاستحقاق المتوقعة (من `target_days`)، البوابات التي ستُحجب، التذكيرات التي ستُرسل وتواريخها. لا كتابة.
5. **نشر**: يشغّل الفحص، يعرض الفروقات عن الإصدار السابق، ويكتب `payment_plan_versions` جديداً. نص واضح:
   «يسري على الطلبات التي يُعتمد اتفاقها بعد الآن؛ X طلباً قائماً يبقى على الإصدار N».
6. **على مستوى الطلب** (P-38): «تغيير الخطة» يختار خطة/إصدار آخر أو يعدّل الأسطر (موجود `replace`) مع نفس القيود.

### 3.4 قواعد التحقق

| الكود | القاعدة |
|---|---|
| `plan_empty` | سطر واحد على الأقل، 12 كحد أقصى (`MAX_DUES`) |
| `plan_sum` | Σ النسب = 10000bp إن لم يوجد `rest`؛ `rest` واحد فقط وفي آخر الجدول؛ المبالغ الثابتة تُفحص عند الربط بالاتفاق (> القيمة → رفض كما اليوم) |
| `plan_key` | `key` بنمط `^[a-z0-9_]{1,30}$` وفريد |
| `trigger_unknown` | الحدث من الكتالوج؛ `stage_key` موجود في المسار المنشور |
| `trigger_before_unpredictable` | إزاحة سالبة على حدث بلا تاريخ مخطط → تحذير/رفض |
| `trigger_order` | تحذير إن كانت دفعة لاحقة تستحق قبل سابقة (ترتيب التخصيص الأقدم أولاً يعتمد على `position`) |

### 3.5 الإصدارات

- النشر يُنشئ إصداراً immutable (نفس guard `FlowVersion`).
- **التثبيت**: عند `OrderSchedule::sync` لأول اتفاق: اختيار الخطة (شروط الانطباق ← الافتراضية)، تخزين
  `payment_plan_version_id`، نسخ الأسطر إلى `order_dues` بما فيها `trigger` و`grace_days` و`reminder_policy`
  (نسخة مجمّدة — تغيير الخطة لاحقاً لا يمس الطلب).
- **تغيير الاتفاق (M-09)**: يعيد حساب المبالغ من **نفس الإصدار المثبّت** (كما يحدث اليوم مع النسب).
- **ترقية طلب قائم** لإصدار أحدث: إجراء صريح بـ P-38 يمر بـ `replace()`؛ لا ترحيل جماعي صامت.

### 3.6 الترحيل من القاعدة الحالية

1. Migration (`#[Expand]`): الجداول الجديدة والأعمدة nullable.
2. Seeder idempotent: ينشئ خطتين `half` و`single` بإصدار 1 مطابق حرفياً لـ `OrderSchedule::TEMPLATES`
   (`payment_stage` → `stage.started` + `stage_key` للمرحلة التي تحوي `payment_check` بالمرجع `final` في المسار
   المنشور)، `half` افتراضية.
3. الطلبات القائمة: `payment_plan_version_id = NULL` = «قديم»؛ `DueCalendar` يبقي فرع `due_event` القديم لها. لا
   تعديل لـ `order_dues` القائمة.
4. `DueEvent` يُوسّع بدل الاستبدال (`payment_stage` يبقى مقروءاً).
5. `payment_check` بأساس `percent` في المسارات المنشورة يبقى يعمل. محرّر المسار يعرض تنبيه «هذه البوابة تكرر نسبة
   الخطة؛ حوّلها إلى (دفعة مسددة)» مع زر تحويل في المسودة.
6. بعد تبنّي كل المنشآت: `#[Contract]` يزيل الثوابت من `OrderSchedule` (يبقى قالب احتياطي للاختبارات).

## 4. معمارية الـ No-Code في OpsOne

### 4.1 محرّك قواعد/أتمتة مشترك

```text
 مصادر الأحداث (موجودة)                 طبقة جديدة                               التنفيذ (موجود)
 ─────────────────────                 ──────────                               ───────────────
 state_transitions (كل الآلات) ─┐
 AgreementApplied / Delivery-    ├─▶ EventNormalizer ─▶ automation_events ─▶ RuleMatcher ─▶ automation_runs ─▶ ActionCatalogue ─▶ Notifier / CustomerMessenger (Outbox)
 Confirmed / RefundExecuted      │     (after commit)    (typed payload)      (published     (idempotent)      (typed, allow-     Task Actions (M-07)
 Scheduler (مؤقتات)  ───────────┘                                             rule versions)                    listed)            Remarks / Holds
                                                                              automation_timers ◀── delay ──┘
```

- **الأحداث**: كتالوج مغلق في الكود (`AutomationEvent` enum) — كل حدث له مخطط payload مكتوب الأنواع وحقول قابلة
  للشرط (allow-list). يُشتق من `state_transitions` (machine + transition) ومن الأحداث الثلاثة بعد الـ commit. لا
  أحداث «عامة» على أي تغيير Eloquent.
- **الشروط**: AST JSON (`all/any/not`، مقارنات `= ≠ > < in contains between`) على حقول مُعلنة فقط: قيمة الطلب، فئة
  المنتج، الفرع، المرحلة، المصدر، حقول مخصّصة، أيام منذ. لا تعابير نصية ولا كود.
- **الإجراءات** (كتالوج مغلق):

  | الإجراء | ينفّذ عبر | مسموح؟ |
  |---|---|---|
  | إرسال رسالة للعميل (قالب) | `CustomerMessenger` | ✅ |
  | إشعار موظف/دور/قسم | `Notifier` | ✅ |
  | إنشاء مهمة متابعة | Action M-07 | ✅ |
  | إسناد مهمة | M-07-T01 مع `TaskEligibility` | ✅ |
  | إضافة ملاحظة/وسم على الطلب | Action | ✅ |
  | إنشاء مسودة أمر شراء | Action M-13-T00 (مسودة) | ✅ |
  | تأخير ثم إجراء | `automation_timers` | ✅ |
  | تسجيل دفعة / استرداد / تخصيص / حركة مخزون / تغيير سعر / إغلاق طلب / تجاوز بوابة | — | ⛔ أبداً |

- **التنفيذ**: listener بعد الـ commit يكتب `automation_events`؛ job على الطابور يطابق القواعد ويكتب
  `automation_runs` بمفتاح `(rule_version_id, event_id, action_index)` فريد → إعادة التشغيل لا تكرر. الإجراء يعمل
  بهوية **«النظام نيابة عن القاعدة»** (`source = automation`) مع تسجيل `state_transitions.source` و`audit_events`
  باسم القاعدة وإصدارها.
- **المؤقتات**: `automation_timers(run_at, payload, cancelled_at)` + أمر مجدول كل دقيقة (نفس نمط `outbox:process`)؛
  يعيد فحص الشرط عند التشغيل (مثل `finance:remind` الذي يعيد فحص المبلغ).
- **الحماية من الحلقات**: عمق سلسلة ≤ 3 (حدث سببه قاعدة يحمل `causation_depth`)، والقاعدة لا تُطلق على حدث صنعته هي.

### 4.2 الإصدارات، المسودة/النشر، والمحاكاة

- **Configuration Release**: كل كائن تهيئة (مسار، خطة دفع، قاعدة، قالب رسالة/مستند، نموذج حقول، سياسة) له مسودة
  و`*_versions` immutable. النشر يمكن أن يكون **حزمة** (`config_releases`: قائمة إصدارات تنشر ذرّياً) حين تعتمد العناصر
  على بعضها (بوابة `due_paid` + خطة جديدة). فحص الحزمة = اتحاد `FlowCheck` + فحص الخطط + فحص القواعد + فحص الترابط.
- **التثبيت**: ما يؤثر على مسار الطلب أو ماله (مسار، خطة، سياسة عمولة، قالب عقد) **يُثبّت عند البدء**. ما هو تواصلي
  (قواعد إشعار، قوالب رسائل) **يسري على الأحداث الجديدة** فقط (لا تثبيت؛ أبسط وأوضح للمستخدم).
- **المحاكاة (dry-run)**: `Simulator::forOrder(order, draft)` يعيد: الدفعات والمبالغ والتواريخ، البوابات، القواعد التي
  ستُطلق على آخر N أحداث للطلب، والرسائل بنصها المعروض. يعمل داخل transaction يُلغى (rollback) أو على نسخة قراءة،
  ولا يكتب Outbox أبداً (`Outbox` في وضع `fake`).
- **Backtest خفيف**: «لو كانت هذه القاعدة منشورة الشهر الماضي: 214 رسالة، 31 مهمة» — يقرأ `automation_events` المؤرشفة.

### 4.3 التدقيق والصلاحيات

- كل حفظ مسودة/نشر/أرشفة → `audit_events` (before/after + `definition_hash`)، صفحة «سجل التهيئة» بفروقات مقروءة.
- صلاحيات جديدة (أرقام تقريبية، تُحدد في ADR):
  - **P-103 تحرير التهيئة** (مسودات) — المدير.
  - **P-104 نشر التهيئة** — المالك افتراضياً؛ لا يجتمع مع P-103 لنفس الشخص إن فعّلت المنشأة «مبدأ الأربع أعين».
  - **P-105 إدارة الأتمتة** (قواعد الرسائل والمهام).
  - التهيئة المالية (خطط الدفع، حدود التجاوز، سياسة العمولة، الترقيم) **للمالك فقط** كما `UpdateCashProofPolicy`.
- `is_support` (ADR-0008) قراءة فقط دائماً — لا ينشر تهيئة.

### 4.6 تصدير/استيراد التهيئة بين النُسخ (instance-per-tenant)

- **الصيغة**: `opsone-config.json` بـ `schema_version`، `app_version_min`، و`items[]` كل منها `{kind, key, definition,

- **الاستيراد** = مسودة دائماً: شاشة diff (جديد/مختلف/متطابق)، حلّ المراجع (قسم غير موجود → اختر بديلاً)، ثم فحص الحزمة،

- **الاستخدام**: (1) حزم الصناعة؛ (2) نقل من بيئة تجربة/demo إلى الإنتاج للمنشأة نفسها؛ (3) لاحقاً: التطبيق المركزي
  (ADR-0003) يوزّع حزماً موقّعة. التوقيع اختياري الآن، إلزامي حين يأتي من المركز.

## 6. خارطة الطريق

### المرحلة 1 — مكاسب سريعة (حجم: **M** إجمالاً، كل بند S)

لا محرّك جديد؛ إعدادات مكتوبة الأنواع بنفس نمط `FinanceSettings` + `Audit`.

1. **خطط دفع قابلة للاختيار (نسخة أولى)**: تحويل `OrderSchedule::TEMPLATES` إلى جدول `payment_plans` بلا إصدارات بعد
   (نسخ الأسطر إلى `order_dues` يكفي للتثبيت)؛ إضافة محفّزات `contract.approved`, `design.approved`,
   `stage.started(stage_key)`, `delivery.completed`، و`offset_days`، و`grace_days`. اختيار الخطة الافتراضية للمالك.
2. **سياسة التذكير** للتحصيل (قبل/بعد/حد/تصعيد) ومواعيد واتساب (24 ← قابل).
3. **بيانات المنشأة الضريبية** (السجل، الرقم الضريبي، العنوان الوطني) — **شرط لـ ZATCA**.
4. **مكتبة بنود العقد والعرض** (نص بمتغيرات مغلقة، إصدار يُخزّن في المستند).
5. **قوالب رسائل** SMS/البريد/داخلي قابلة للتحرير + ربط أسماء قوالب واتساب المعتمدة لكل منشأة.
6. **SLA المهام**: تعبئة `due_at` بأيام العمل + إرسال `work.reminder` المعرّف أصلاً + تصعيد بسيط.
7. **صيغة الترقيم** ورقم البداية.

الاعتمادات: لا شيء جديد. المخاطر: تعارض مع PR ZATCA في ملف المنشأة (تنسيق)؛ الترحيل الصحيح للطلبات القائمة.

### المرحلة 2 — محرّك القواعد وخطط الدفع الكاملة (حجم: **L**)

1. `payment_plan_versions` + التثبيت على `order_finances` + شروط الانطباق + المحاكاة (القسم 3 كاملاً).
2. `payment_check` بأساس `due_paid` + تحويل البوابات القديمة + فحص الترابط عند النشر.
3. حدود التجاوز (`allow_proceed_limits`) — يغلق ADR-0012 gap 6.
4. محرّك الأتمتة (4.1): كتالوج أحداث، شروط AST، كتالوج إجراءات، مؤقتات، runs idempotent، شاشة «قواعد» بنموذج
   «عندما … إذا … فافعل …»، محاكاة وbacktest.
5. `config_releases` (نشر حزمة) + سجل التهيئة + الصلاحيات P-103..105.
6. حزم الصناعة الثلاث + تصدير/استيراد.

الاعتمادات: المرحلة 1 (المحفّزات والقوالب). المخاطر: تكرار رسائل عند إعادة المحاولة (يُعالج بالمفاتيح)؛ حمل
الطابور (حدود 4.4)؛ تعقيد UX للبوابات مع الخطط (يُعالج بعمود «يحجب»).

### المرحلة 3 — الـ Builders (حجم: **L**، قابلة للتقسيم)

1. حقول مخصّصة (عميل، طلب، بند، مهمة) + استخدامها في الشروط والقوالب والتقارير.
2. نماذج/قوائم فحص للمهام والمحاضر مع توقيع العميل (مع PWA الميداني).
3. سلاسل موافقات متعددة المستويات (خصم، شراء، استرداد) بعتبات مبلغ.
4. مسارات متعددة + اختيار بالقاعدة + شروط حاجة على فئة المنتج.
5. قوالب مستندات PDF بأقسام قابلة للترتيب.
6. Report builder على `MetricCatalogue`.
7. أدوار مخصّصة، شرائح عمولة، BOM بالمعادلات (حسب الطلب التجاري).

الاعتمادات: المرحلة 2 (الشروط والإصدارات والتصدير). المخاطر: أداء الفلترة على الحقول المخصّصة (أعمدة مولّدة مفهرسة
محدودة العدد)؛ اتساع نطاق الاختبار.

### أسئلة لصاحب المنتج

1. هل تُثبّت **قواعد الإشعارات** على الطلب (مثل الخطة) أم تسري على الأحداث الجديدة فقط؟ (التوصية: الأحداث الجديدة.)
2. من ينشر التهيئة المالية: **المالك فقط**، أم المالك + مدير بموافقة ثانية (four-eyes)؟
3. هل نسمح بأكثر من **مسار واحد** لكل منشأة؟ وهل يرتبط عدد المسارات/القواعد **بالباقة** (ترخيص)؟
4. هل يُسمح بالتجاوز (allow proceed) **بدون حد** للمالك، وما الحد الافتراضي للمدير (نسبة أم مبلغ)؟
5. هل الدفعة بنسبة تُحسب على **القيمة شاملة الضريبة** دائماً (كما اليوم)، أم يحتاج B2B نسبة على القيمة قبل الضريبة؟
6. «قبل التركيب بـ N أيام»: نعتمد **التاريخ المخطط** للمرحلة، أم **تاريخ موعد التركيب المؤكد** (M-16)؟
7. هل نوفّر **السنة الهجرية** في الترقيم، ومتى يسري تغيير الصيغة (فوراً برقم بداية أم من السنة التالية)؟
8. هل تبدأ المرحلة 1 قبل دمج PR ZATCA أم بعده (تداخل في ملف المنشأة والترقيم)؟
9. هل تُحرَّر **قوالب واتساب** داخل OpsOne (ويرسلها النظام لاعتماد Meta) أم تبقى مدارة مركزياً من OpsOne؟
10. هل تُوزّع **حزم الصناعة** من التطبيق المركزي لاحقاً، أم تبقى داخل كود التطبيق؟
11. هل تريد **محاكاة إلزامية** قبل النشر (يجب تشغيلها على طلب واحد على الأقل) أم اختيارية؟
