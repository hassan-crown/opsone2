## 2. مجموعة البيانات (Q-55)

`./manage.sh artisan db:seed --class=PerformanceSeeder` بعد `db:seed` (محلي/اختبار فقط، يرفض غيرهما، ~25 ثانية).
حتمية: بذرة PRNG ثابتة (55) ويوم مرجعي = اليوم أو `PERF_SEED_ANCHOR=Y-m-d`.

| orders | 20,001 | 65% تفصيل / 35% جاهز؛ حالات واقعية حسب العمر (الحديث مفتوح غالبًا، القديم مغلق) |

حجم القاعدة: ~166MB بيانات + ~187MB فهارس للمنشأة الواحدة.

**الثوابت المتحقق منها بعد التوليد** (استعلامات SQL مباشرة): 0 قيد تحصيل لا يساوي مبلغ دفعته، 0 قيد تخصيص لا يساوي صفرًا،
0 استحقاق مخصص فوق مبلغه، 0 رصيد مخزون يخالف مجموع حركاته، ولا `on_hand_after`/`reserved_after` سالب.

**القيود المعروفة:** لا تُولَّد اتفاقيات (تعتمد على مستندات وقرارات عميل)، فالاستحقاقات بأحداث «تاريخ». مسار
الاتفاقية/مرحلة الدفع في `DueCalendar` مغطى باختبارات P6 الموجودة وبتجميع الاستعلام نفسه (`datesFor`).

## 3. المنهج

- `./manage.sh artisan perf:probe [--runs=15] [--only=…] [--top=8] [--json=…]`: يمرر كل صفحة عبر HTTP kernel داخل
  العملية نفسها (توجيه، middleware، متحكم، استعلامات، تسلسل)، تشغيلتا إحماء ثم 15 مقاسة، ويعطي p50/p95 وعدد
  الاستعلامات وزمن SQL وحجم الاستجابة. التنقل داخل التطبيق يرسل خصائص once التي يحملها العميل (كما يفعل المتصفح)،
  و«أول KB» حجم أول زيارة.
- المستخدمون: المالك (نطاق المنشأة)، مندوب مبيعات بنطاق فرع، منفّذ، مشرف قسم، مالي بفرعين، وأكثر عميل طلبات في البوابة.
- الحمل المتزامن: `docs/performance/load/load.sh <email> 20 300 /orders …` — يسجل الدخول مرة بجلسة حقيقية ثم `ab` بـ 20
  اتصالًا متزامنًا عبر nginx + PHP-FPM (`PERF_BASE`/`PERF_HOST`/`PERF_PASSWORD` لبيئة أخرى). المخرجات الخام في
  `docs/performance/load/ab-20-concurrent.txt`.
- البيئة: Docker Desktop على macOS (جهاز تطوير)، MariaDB 11، PHP 8.5 مع OPcache، `pm.max_children=5` الافتراضي.
  الأرقام للمقارنة قبل/بعد؛ بيئة الإطلاق تُثبت بقياس عليها (NFR-13 ينص على ذلك).

### 4.2 الحمل المتزامن (NFR-13: 20 مستخدمًا)

`ab -c 20 -n 300` لكل صفحة عبر nginx + PHP-FPM على الإعداد الافتراضي (`pm.max_children=5`، أي أن 20 طلبًا يصطف
على 5 عمال)، بجلسة المالك (أوسع نطاق)، تنقل Inertia بالترجمات المحمّلة، بعد الإصلاحات. 0 طلبات فاشلة، كلها 200.

## 5. ما تغيّر

| المشكلة المقاسة | الإصلاح |
|---|---|
| البوابة: قراءة `access_version` مع كل فحص صلاحية (1,638 مرة في قائمة مهام) | قراءة واحدة كل ثانيتين كحد أقصى لكل عملية، وتفريغ فوري عند أي إلغاء جلسات (ADR-0027 §5) |
| `Facility::current()` لكل صف (1,001 مرة في التقويم) | منطقة الزمن في `RequestCache` لكل طلب، تُفرّغ عند حفظ المنشأة |
| التقويم: فرع وعميل كل موعد كسولًا، فلتر الفرع بعد حد 500 | تحميل مسبق، فلتر الفرع في SQL قبل الحد، حد أدنى لـ `starts_at` (المدة ≤ 72 ساعة) |
| المهام: قسم ومُسند لكل صف، أهلية الإسناد 3 استعلامات لكل صف، قسم المرحلة النشطة لكل طلب | علاقات محمّلة مسبقًا، أهلية مخزنة للطلب، `Order::primeAccessDepartments` |
| المالية: اتفاقية لكل طلب في `DueCalendar` (500 استعلام)، وحد 500 يمتلئ بطلبات مسددة | `DueCalendar::datesFor` (استعلام لكل نوع حدث)، `OpenDues` يحد الطلبات التي عليها مبالغ فقط (تصحيح) |
| المخزون: صنف الكتالوج لكل رصيد/حركة (480 استعلامًا) | `StockItems::preload` |
| البوابة: مالية كل طلب للعميل (~8 استعلامات × كل طلباته)، مرحلة وعنوان لكل طلب مرتين | المالية فقط للطلبات التي تقبل إثباتًا، `PortalPresenter::orders` باستعلامين للقائمة |
| ~600KB ترجمات في كل استجابة Inertia (حتى الاستطلاع الجزئي للإشعارات) | خاصية once بمفتاح اللغة + نسخة الملفات (الموظفون والبوابة بمفتاحين منفصلين) |
| Inertia يمر على كل قيمة متداخلة: 134ms لـ 500 صف | `PropRows` (صفوف ككائنات): 10ms |
| فلاتر الحالة في قائمة الطلبات تمسح الجدول كاملًا | فهارس `orders (status,id)` و`(branch_id,status,id)` و`money_entries (order_due_id,order_id,amount_minor)` |

**ما لم يُفعل ولماذا:** ترقيم keyset (الصفحة 900 من 20,000 طلب ~60ms؛ الكلفة في COUNT لا في الإزاحة)، نقل آثار إلى
الطابور (لا أثر بطيء على مسار قراءة مقاس؛ البريد/SMS عبر outbox أصلًا)، تخزين مؤقت بين الطلبات في Redis (لم يحتجه
أي مسار)، تقليل فحوص الصلاحية لكل صف (لا تُمس الصلاحيات لأجل السرعة).

## 6. الحراسة في الاختبارات (`tests/Feature/Performance/PerformanceGuardsTest.php`)

- ميزانية استعلامات ثابتة لـ 13 صفحة موظفين و3 صفحات بوابة والمتجر (الأرقام نفسها عند ثلاثة أضعاف البيانات).
- الصفحات نفسها بعد تكديس ~100 صف إضافي على المستخدم نفسه وأسبوع اليوم: يجب ألا يزيد العدد (+2 هامش). تحقق: إرجاع
  N+1 واحد في `TaskPresenter` رفع قائمة المنفذ من 39 إلى 81 وأفشل الاختبار.
- `Model::preventLazyLoading` مفعّل خارج الإنتاج (كشف 5 مواضع تحميل كسول في مسارات قائمة وأُصلحت).
- على MariaDB فقط (يُتخطى على SQLite): `EXPLAIN` يثبت أن استعلامات القوائم الأساسية تستطيع استخدام فهرسها المقصود
  ولا تمسح الجدول كاملًا.

رفع أي ميزانية يحتاج سببًا مكتوبًا هنا.

## 7. اقتراحات ضبط الخادم (لمسؤول السيرفر — لم يُعدَّل أي ملف بنية)
